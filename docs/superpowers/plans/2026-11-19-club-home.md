# Club Home Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** When club owners sign in, they land on their own club's dashboard: stats, a 6-week views chart, enquiries, locked Pro tools and a profile-strength checklist. They edit their listing in a 4-step wizard, and the public profile hides empty sections.

**Architecture:** There are no new pages for parents. A `/club/[id]` layout adds two tabs ("Dashboard and Pro", "List your club") and a club switcher. Calculations (weekly buckets, week-on-week change, checklist) live in `lib/domain/dashboard.ts`. Data comes from `lib/services/club.ts` through RLS. A security-definer function gives a club its save count without exposing `saved_clubs`.

**Tech Stack:** Next.js 16 (App Router; read `node_modules/next/dist/docs/01-app` before writing layouts, redirects or route segments), Supabase Postgres + RLS, next-intl, Tailwind 4 brand tokens, Vitest, Playwright + axe.

**Spec:** `docs/superpowers/specs/2026-11-19-demo-round-design.md` (section "1. Club home")

## Global Constraints

- Every UI string goes in `messages/en.json`. No hard-coded copy in components.
- Only brand colour tokens. Logical-direction utilities only (`ms-`, `ps-`, `text-start`, …). `tests/unit/source-rules.test.ts` enforces this.
- The words `billing`, `invoice`, `checkout`, `stripe` and `payment_intent` must not appear in `app/`, `components/` or `lib/` code. That includes message keys used in code. Name the Pro card key `payments`, never `billing`. The display copy lives in `messages/en.json`, which is fine.
- Tap targets are at least 44 px (`min-h-tap`). Pages pass axe (WCAG 2.2 AA) at 360 px and at 200 % zoom with no horizontal scroll.
- Ranking never reads anything added here (fair-order and parity tests stay green).
- Numbers are real counts from the database. Zero and small numbers are shown as they are.
- Pro tools are always shown locked and link to `/club/upgrade`. No prices anywhere.
- Each migration is a new file in `supabase/migrations/`. Grants are explicit, and a function is callable only as the spec says.
- No new npm dependencies in this plan.

## Review Focus

1. **Club owner with two clubs.** The demo account owns Oryx Owls and Camel Cove. `/club` lands on the first approved club, sorted by name, and the switcher reaches the other. A test is in Task 4.
2. **Signed-in club user with zero clubs** (new sign-up). `/club` must not redirect-loop. It shows the "add your club" prompt. A test is in Task 4.
3. **Club with no views at all.** The chart renders six zeros with a flat line, the week change shows "No change" rather than `NaN%` or `Infinity`, and the zero illustration still shows. A test is in Task 2 (domain) and Task 5 (e2e on Camel Cove).
4. **Someone who doesn't manage the club** opening `/club/[id]` gets a 404. Calling `club_save_count` for someone else's club returns null. Tests are in Task 1 (RLS) and Task 4 (e2e).
5. **Old links** to `/club/[id]/demand` (e.g. bookmarks, existing e2e) redirect to the dashboard enquiries anchor. A test is in Task 5.

### Task 2: Dashboard maths

**Interfaces:**
- Produces:
  - `weeklyCounts(timestamps: string[], now: Date, weeks = 6): number[]`. The result is oldest first. Bucket `i` covers `[now − (weeks−i)·7d, now − (weeks−i−1)·7d)`, and timestamps outside every bucket are ignored.
